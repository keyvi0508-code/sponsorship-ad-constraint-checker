# Synthetic model-input leakage audit

The 60 saved synthetic rows all include `ground_truth` because they are labelled evaluation data. Passing those raw rows to the model would expose the answer in **60/60** requests. The actual review path now uses an explicit field allowlist in [`case_for_model`](../src/validate_data.py), rather than merely deleting three known label names. It retains the script fields needed for review and drops `ground_truth`, `annotator_notes`, `dataset_split`, and any newly introduced fields outside that allowlist.

`python scripts/audit_model_input_leakage.py` constructs the same two request payload shapes used by the saved synthetic reviewer for all 60 rows, without making an API call. The reproducible audit found **0/60 Stage 1** and **0/60 Stage 2** payloads containing private label or split fields. In a stress check, an added `expected_verdict` and `model_hint` were also excluded in **60/60** cases. A separate test sends a labelled case through a mocked two-stage review and checks both captured requests. The full test suite passes.

This is a **payload-exposure check**, not a before/after accuracy experiment. A run deliberately handed `ground_truth` could trivially copy the target and would be contaminated by design. Its score would not estimate review quality, so no leaked-input model score is claimed. The historical AI scores remain development evidence on project-authored examples with disputed labels. For a stronger future leakage study, create fresh cases whose labels and rationales are stored outside the model input pipeline, lock all prompts, and audit provider-side request records where available.
